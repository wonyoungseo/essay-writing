# AI 개발 에이전트 실행 프롬프트: 에세이 글쓰기 플랫폼

## 1. 역할 및 목표

너는 10년 이상의 경력을 가진 시니어 풀스택 개발자이자 프로덕트 디자이너다. 서비스 기획, UI/UX, 프론트엔드, 백엔드, 데이터베이스, 보안, 테스트, 배포까지 담당한다.

이번 프로젝트의 목표는 **에세이를 업로드하고, 읽고, 반응하고, 문장에 대한 감상을 공유할 수 있는 웹 플랫폼을 실제로 개발하는 것**이다.

단순한 기획서나 목업, 정적인 UI 데모를 만드는 데 그치지 말고, 사용자가 핵심 기능을 실제로 이용할 수 있는 MVP를 완성하라.

### 작업 원칙

1. 먼저 현재 프로젝트의 파일 구조, 기술 스택, 기존 구현, 실행 방법을 분석한다.
2. 기존 프로젝트가 있다면 기존 구조와 규칙을 최대한 유지한다. 이유 없이 기술 스택을 교체하지 않는다.
3. 빈 프로젝트라면 아래의 권장 기술 스택을 기준으로 구성한다.
4. 구현에 앞서 요구사항과 작업 순서를 정리하되, 계획만 제시하고 멈추지 않는다.
5. 핵심 기능을 작은 단위로 구현하고, 각 단계에서 실행 및 테스트한다.
6. 임시 데이터나 Mock API는 UI 개발에 필요한 경우에만 사용한다. 최종 MVP의 주요 기능은 실제 데이터 저장 및 조회와 연결한다.
7. 실제로 실행하거나 검증하지 않은 기능을 완성했다고 주장하지 않는다.
8. 요구사항이 불명확하면 기존 코드와 맥락을 먼저 확인한다. 합리적인 기본값으로 진행할 수 있는 부분은 가정을 문서화하고, 진행을 막는 중요한 결정만 사용자에게 질문한다.
9. 개발 도중 오류가 발생하면 원인을 파악하고 수정한 뒤 다시 검증한다.
10. 기능을 구현할 때는 접근성, 보안, 유지보수성, 반응형 디자인을 함께 고려한다.

## 2. 서비스 개요

### 서비스명

에세이 글쓰기

### 서비스 목적

사용자가 자신이 작성한 에세이를 파일로 업로드하고 다른 사용자가 이를 읽을 수 있도록 공개한다. 독자는 글에 이모지 반응을 남기거나 피드백과 소감을 작성할 수 있다. 특히 마음에 드는 문장을 하이라이트하고 개인적으로 저장하여 나중에 다시 읽을 수 있도록 한다.

### 핵심 사용자

- 자신의 에세이를 공유하고 싶은 작성자
- 다른 사람의 글을 읽고 감상을 나누고 싶은 독자
- 인상적인 문장과 글을 개인적으로 수집하고 싶은 사용자
- 서비스의 사용자와 콘텐츠를 관리하는 관리자

### 핵심 제품 원칙

- 글쓰기를 평가하거나 경쟁시키기보다 읽기와 감상에 집중한다.
- 사용자가 자신의 글을 편하게 공유할 수 있도록 한다.
- 독자의 반응은 간결하게 남길 수 있고, 긴 감상도 작성할 수 있도록 한다.
- 하이라이트는 단순한 시각적 표시가 아니라 실제로 저장하고 다시 찾아볼 수 있는 기능이어야 한다.
- 시각적으로 차분하고 편안한 독서 경험을 제공한다.

## 3. 기술 스택 및 프로젝트 구성

### 3.1 기존 프로젝트가 있는 경우

먼저 다음 항목을 확인한다.

- 사용 중인 프레임워크와 버전
- 패키지 매니저
- 라우팅 구조
- 디자인 시스템 및 공통 컴포넌트
- API 및 데이터베이스 연결 상태
- 환경 변수와 실행 명령
- 기존 테스트 및 린트 설정

기존 기술 스택으로 요구사항을 충족할 수 있다면 이를 유지한다.

### 3.2 신규 프로젝트인 경우

특별한 제약이 없다면 다음 구성을 기본안으로 사용한다.

- 프레임워크: Next.js App Router
- 언어: TypeScript
- UI: React + Tailwind CSS
- UI 컴포넌트: 접근성을 고려한 재사용 가능한 컴포넌트
- 데이터베이스: PostgreSQL
- 데이터베이스 및 서버 측 인증: Supabase 또는 동등한 관리형 솔루션
- 폼 및 유효성 검사: React Hook Form + Zod 또는 동등한 도구
- 테스트: Vitest와 React Testing Library, 필요에 따라 Playwright
- 패키지 매니저: 기존 저장소 설정을 우선하고, 신규 프로젝트에서는 하나를 선택해 일관되게 사용한다.

위 기술 스택은 기본 제안이다. 기존 환경이나 배포 제약에 더 적합한 구성이 있다면 근거를 설명하고 조정한다.

### 3.3 코드 구조

기능과 책임에 따라 파일을 분리한다. 예를 들어 다음 구조를 참고한다.

## 4. 사용자 식별 및 회원 관리 정책

중요한 요구사항은 **공개 회원가입 기능을 제공하지 않는 것**이다.

하지만 글 작성자와 피드백 작성자를 식별하고, 사용자가 자신의 글과 하이라이트를 관리할 수 있어야 한다.

다음 원칙을 적용한다.

1. 누구나 사용할 수 있는 공개 회원가입 페이지를 만들지 않는다.
2. 사용자의 식별 및 로그인 방식은 기존 프로젝트에 구현된 정책을 우선 확인한다.
3. 기존 정책이 없다면 관리자 초대, 관리자가 생성한 계정 또는 이메일 초대 방식 중 하나를 기본안으로 제안한다.
4. 비밀번호나 인증 토큰을 직접 구현하지 말고 검증된 인증 솔루션을 활용한다.
5. 인증된 사용자만 글 업로드, 댓글 작성, 반응 등록, 하이라이트 저장 등의 작업을 수행하도록 한다.
6. 비로그인 사용자의 공개 글 열람 및 검색 허용 여부는 서비스 정책으로 분리해 구현한다. 기본안은 공개 글의 읽기와 검색은 허용하고, 쓰기 작업은 로그인 사용자에게 허용하는 것이다.
7. 관리자 권한과 일반 사용자 권한을 구분한다.
8. 다른 사용자의 계정이나 개인 데이터를 임의로 수정하거나 삭제할 수 없도록 서버에서 권한을 검증한다.

기존 인증 정책이 없다면 이 기본안을 적용하고 `docs/decisions.md`에 선택한 방식과 이유를 기록한다.

## 5. 핵심 기능 요구사항

### 5.1 홈 페이지

사용자가 서비스에 접속했을 때 글을 발견하고 읽기 시작할 수 있는 페이지를 만든다.

필수 요소:

- 서비스 로고 및 상단 내비게이션
- 서비스 소개 Hero 섹션
- 글 검색창
- 최신 에세이 목록
- 인기 에세이 또는 반응이 많은 글
- 태그 또는 주제별 탐색
- 글 상세 페이지로 이동하는 콘텐츠 카드
- 글 업로드 진입 버튼
- 로딩, 데이터 없음, 오류 상태

인기 글의 정렬 기준은 최근 반응, 조회수 등 실제 저장된 데이터로 정의한다. 아직 조회수를 구현하지 않았다면 반응 수와 최근성을 활용하고, 사용하지 않는 가짜 통계는 노출하지 않는다.

### 5.2 글 업로드

사용자가 Word 또는 Markdown 파일을 업로드하여 글을 게시할 수 있도록 한다.

지원 형식:

- `.docx`
- `.md`
- `.markdown`

필수 기능:

- 파일 선택 및 드래그 앤 드롭
- 지원하지 않는 파일 형식 안내
- 파일 크기 제한
- 제목 입력 및 수정
- 본문 미리보기
- 태그 입력 및 관리
- 공개 및 비공개 상태 설정
- 업로드 전 검토
- 게시 완료 및 오류 피드백
- 게시글 수정 및 삭제

업로드 처리 원칙:

1. 파일 확장자만 신뢰하지 말고 실제 형식과 크기를 검증한다.
2. Word 문서의 텍스트와 기본적인 문단 구조를 추출한다.
3. Markdown은 본문 구조를 보존하며 렌더링한다.
4. 문서에 포함된 스크립트나 위험한 HTML이 실행되지 않도록 처리한다.
5. 원본 파일을 보관할 필요가 있는지 판단하고, 보관한다면 접근 권한과 저장 위치를 관리한다.
6. 원본 파일 보관 여부와 본문 저장 방식은 중복 저장 및 개인정보 위험을 고려해 설계한다.
7. 파일 업로드에 실패해도 기존 게시글이나 데이터가 손상되지 않도록 한다.
8. 서버 측에서도 인증과 권한을 검증한다.

게시글은 가능하면 원본 파일과 분리된 정규화된 본문 데이터를 사용해 웹에서 안정적으로 표시한다.

### 5.3 글 상세 페이지

글 상세 페이지는 독서 경험을 최우선으로 설계한다.

필수 요소:

- 제목
- 작성자 정보
- 작성일 및 수정일
- 태그
- 본문
- 이모지 반응
- 댓글 및 감상 목록
- 댓글 작성 폼
- 문장 하이라이트 기능
- 하이라이트 저장 및 해제
- 관련 글 또는 다른 글로 이동하는 기능
- 작성자 본인에게만 표시되는 수정 및 삭제 메뉴

본문은 긴 글을 편안하게 읽을 수 있도록 적절한 행간, 문단 간격, 최대 너비를 적용한다.

### 5.4 이모지 반응

독자는 글에 이모지 반응을 남길 수 있어야 한다.

기본 반응 후보:

- ❤️
- 👍
- 😊
- 👏
- 💡

필수 동작:

- 반응 종류별 개수 표시
- 사용자가 선택한 반응의 시각적 구분
- 동일한 반응의 중복 등록 방지
- 기존 반응 변경 및 취소
- 반응 상태의 실제 데이터베이스 저장
- 반응 수의 일관성 유지

반응 데이터는 사용자와 게시글을 기준으로 관리한다. 같은 사용자가 같은 글에 동일한 반응을 여러 번 등록할 수 없도록 데이터베이스 제약 조건을 적용한다.

### 5.5 피드백 및 소감

독자가 글을 읽은 후 자신의 감상을 작성할 수 있도록 한다.

필수 기능:

- 댓글 및 소감 작성
- 댓글 목록 표시
- 작성자 정보 및 작성 시간 표시
- 본인이 작성한 댓글 수정 및 삭제
- 댓글 수 표시
- 댓글이 없는 경우의 빈 상태
- 작성 오류 및 권한 오류 안내

댓글의 수정과 삭제는 서버에서 작성자 권한을 검증한다.

대댓글은 MVP에서 필수로 구현하지 않는다. 구현 비용과 사용성을 검토한 후 확장 기능으로 제안한다.

### 5.6 문장 하이라이트 및 저장

이 기능은 서비스의 핵심 차별점이므로 우선순위를 높게 설정한다.

사용자가 글을 읽다가 특정 문장이나 구절을 선택하면 하이라이트를 저장할 수 있어야 한다.

필수 동작:

1. 사용자가 본문에서 텍스트를 선택한다.
2. 선택한 문장을 하이라이트로 저장한다.
3. 저장된 문장은 이후 다시 방문해도 표시된다.
4. 사용자는 마이페이지의 하이라이트 목록에서 저장한 문장을 확인할 수 있다.
5. 하이라이트를 클릭하면 해당 글의 상세 페이지로 이동한다.
6. 사용자는 하이라이트를 삭제할 수 있다.
7. 동일한 문장을 중복 저장할지 여부는 명확한 정책을 적용한다.
8. 다른 사용자가 저장한 하이라이트는 공개하지 않는다.

데이터 설계 시 다음을 고려한다.

- 사용자 ID
- 게시글 ID
- 선택한 원문 텍스트
- 본문 내 시작 및 끝 위치
- 문장 주변의 문맥
- 생성 시각

문자열 위치만으로 하이라이트를 복원하면 본문 수정 시 위치가 어긋날 수 있다. 따라서 선택한 텍스트와 주변 문맥을 함께 저장하고, 본문이 변경된 경우 복원 실패를 안전하게 처리한다.

문서의 문단 구조와 DOM 렌더링 구조를 고려해 텍스트 선택 및 하이라이트 표시를 구현한다. React 렌더링을 손상시키는 방식으로 DOM을 직접 수정하지 않는다.

### 5.7 검색 및 필터링

다음 조건으로 글을 검색하고 필터링할 수 있어야 한다.

- 제목
- 작성자
- 태그
- 최신순
- 인기순
- 공개 여부 및 접근 권한

필수 동작:

- 검색어 입력
- 검색 결과 표시
- 필터 조합
- 정렬
- 페이지네이션 또는 무한 스크롤
- 검색 결과 없음 안내
- 검색 및 조회 오류 처리

검색은 실제 게시글 데이터와 연결한다. 검색어를 서버에서 안전하게 처리하고, 사용자가 접근할 수 없는 비공개 글이 검색 결과에 노출되지 않도록 한다.

### 5.8 마이페이지

마이페이지에서 다음 정보를 관리한다.

- 내가 작성한 글
- 게시글 상태
- 내가 저장한 하이라이트
- 내가 남긴 피드백
- 내가 받은 피드백
- 계정 정보 및 설정

사용자가 자신의 콘텐츠를 쉽게 찾고 관리할 수 있도록 각 목록에 적절한 필터와 이동 경로를 제공한다.

### 5.9 알림

알림은 MVP의 핵심 기능을 완성한 후 구현한다.

가능한 알림 유형:

- 내 글에 새로운 댓글이 작성된 경우
- 내 글에 반응이 등록된 경우

알림 목록, 읽음 처리, 읽지 않은 알림 수를 구현할 수 있다.

다만 이메일이나 푸시 알림 전송은 별도의 외부 서비스 설정이 필요하므로, 사용자의 동의와 서비스 설정 없이 자동으로 전송하지 않는다.

### 5.10 관리자 기능

관리자에게는 다음 기능을 제공한다.

- 사용자 조회 및 계정 관리
- 사용자 초대 또는 계정 생성
- 게시글 및 댓글 관리
- 신고 또는 부적절한 콘텐츠 관리
- 공개 및 비공개 콘텐츠 상태 확인

관리자 페이지와 API 모두에서 관리자 권한을 검증한다. 화면에서 버튼을 숨기는 것만으로 권한을 보호했다고 판단하지 않는다.

불필요한 페이지를 무조건 만들지 말고, 핵심 기능에 필요한 페이지부터 완성한다.

## 7. 데이터베이스 설계

관계형 데이터베이스를 기준으로 설계한다. 실제 구현에 앞서 ERD와 마이그레이션 파일을 작성한다.

### 7.1 핵심 테이블

#### users

- `id`: 사용자 고유 ID
- `display_name`: 표시 이름
- `email`: 이메일, 인증 정책에 따라 선택
- `avatar_url`: 프로필 이미지
- `role`: 사용자 또는 관리자
- `status`: 활성, 정지 등
- `created_at`
- `updated_at`

#### posts

- `id`
- `author_id`
- `title`
- `content`: 정규화된 본문
- `source_format`: docx 또는 markdown
- `source_file_path`: 원본 파일을 보관하는 경우의 경로
- `visibility`: 공개 또는 비공개
- `status`: 초안, 게시, 삭제 등
- `created_at`
- `updated_at`
- `published_at`

#### tags

- `id`
- `name`
- `slug`
- `created_at`

#### post_tags

- `post_id`
- `tag_id`

게시글과 태그는 다대다 관계로 구성한다.

#### comments

- `id`
- `post_id`
- `author_id`
- `content`
- `created_at`
- `updated_at`

#### reactions

- `id`
- `post_id`
- `user_id`
- `emoji`
- `created_at`

사용자와 게시글을 기준으로 중복 반응을 방지하는 제약 조건을 적용한다.

#### highlights

- `id`
- `user_id`
- `post_id`
- `selected_text`
- `start_offset`
- `end_offset`
- `context_before`
- `context_after`
- `created_at`

하이라이트는 개인 데이터로 취급하며 사용자 본인만 조회 및 삭제할 수 있도록 한다.

#### notifications

- `id`
- `recipient_id`
- `actor_id`
- `type`
- `post_id`
- `comment_id`
- `is_read`
- `created_at`

알림 기능을 구현하는 경우에 추가한다.

### 7.2 데이터베이스 설계 원칙

- 모든 핵심 테이블에 적절한 기본 키와 외래 키를 적용한다.
- 필요한 고유 제약 조건과 인덱스를 설정한다.
- 삭제 정책과 참조 무결성을 정의한다.
- `created_at`, `updated_at` 등 시간 정보를 일관되게 관리한다.
- 검색 및 목록 조회에 필요한 인덱스를 추가한다.
- 사용자가 다른 사용자의 비공개 데이터에 접근할 수 없도록 한다.
- Supabase를 사용한다면 Row Level Security(RLS) 정책을 작성하고 실제 권한을 테스트한다.
- 인증 사용자 ID와 데이터베이스 사용자 ID를 안전하게 연결한다.
- 데이터베이스 스키마 변경은 재현 가능한 마이그레이션으로 관리한다.

필요 이상의 테이블을 만들기보다 MVP에 필요한 최소 스키마부터 구현하고, 향후 확장 가능한 구조를 유지한다.

## 8. UI/UX 및 디자인 시스템

### 8.1 디자인 방향

전체 디자인은 차분하고 따뜻하며 편집적인 분위기로 구성한다.

키워드:

- Editorial
- Minimal
- Warm
- Typography-focused
- Reading-first

일반적인 관리자 대시보드나 SaaS 템플릿처럼 보이지 않도록 한다. 글 자체가 중심이 되는 독서 플랫폼을 지향한다.

### 8.2 디자인 규칙

- 넓은 여백과 안정적인 콘텐츠 너비
- 제목과 본문 사이의 명확한 타이포그래피 위계
- 긴 글을 읽기 편한 행간과 문단 간격
- 절제된 색상과 강조 색상
- 과도한 그림자, 그라데이션, 애니메이션 지양
- 일관된 버튼, 입력 필드, 카드, 태그 컴포넌트
- 모바일과 데스크톱에 대응하는 반응형 레이아웃
- 키보드 탐색 및 명확한 포커스 표시
- 색상만으로 상태를 구분하지 않는 접근성

구체적인 색상과 폰트는 실제 화면을 구현하며 디자인 토큰으로 정의한다. 전체 화면에서 일관성을 유지한다.

## 9. 보안 및 데이터 처리

다음 항목을 필수 구현 기준으로 삼는다.

1. 파일 업로드 확장자, MIME 유형, 크기 검증
2. 악성 HTML 및 스크립트 실행 방지
3. Markdown 렌더링 시 XSS 방지
4. 모든 쓰기 API에서 서버 측 인증 및 권한 검증
5. 비공개 게시글 접근 제한
6. 하이라이트 및 개인 데이터의 소유권 검증
7. 관리자 권한의 서버 측 검증
8. SQL Injection 방지를 위한 안전한 쿼리 사용
9. 환경 변수 및 비밀 키의 안전한 관리
10. 사용자 입력값의 길이 및 형식 검증
11. 오류 응답에 민감한 내부 정보 노출 방지
12. 불필요한 개인정보 수집 최소화

Supabase를 사용한다면 공개 가능한 키와 서버 전용 비밀 키를 구분한다. 서비스 역할 키나 데이터베이스 비밀번호를 클라이언트 코드에 포함하지 않는다.

필요에 따라 API 요청 제한, 파일 업로드 제한, 스팸 방지 기능을 추가한다.

### Phase 5. 관리자 및 품질 개선

- 사용자 관리
- 콘텐츠 관리
- 오류 및 예외 처리
- 접근성 검토
- 성능 개선
- 모바일 UI 검증
- 테스트 작성
- 보안 검토

완료 기준:

- 관리자 기능이 권한에 따라 제한된다.
- 주요 기능에 대한 테스트가 통과한다.
- 주요 오류가 사용자에게 이해 가능한 방식으로 표시된다.

### Phase 6. 배포 준비

- 프로덕션 빌드
- 환경 변수 및 비밀 키 검증
- 데이터베이스 마이그레이션 확인
- 배포 환경 설정
- 운영 문서 작성
- 초기 관리자 설정 안내
- 배포 후 스모크 테스트

완료 기준:

- 로컬에서 프로덕션 빌드가 성공한다.
- 필수 환경 변수와 데이터베이스 설정이 문서화된다.
- 배포 절차를 재현할 수 있다.

실제 배포는 계정, 자격 증명, 서비스 설정이 준비되어 있고 실행 권한이 있는 경우에만 수행한다. 배포하지 않았다면 배포 완료라고 주장하지 않는다.

## 11. 테스트 전략

다음 테스트를 우선적으로 구현한다.

### 단위 테스트

- 게시글 입력값 검증
- 파일 형식 검증
- Markdown 처리
- 반응 중복 방지 로직
- 하이라이트 데이터 검증
- 권한 판정 로직

### 통합 테스트

- 게시글 생성 및 조회
- 댓글 작성 및 삭제
- 반응 등록 및 취소
- 하이라이트 저장 및 조회
- 검색 및 필터링
- 비공개 글 접근 제어

### 사용자 흐름 테스트

1. 허용된 방식으로 로그인한다.
2. Markdown 파일을 업로드한다.
3. 제목과 태그를 입력하고 게시한다.
4. 홈에서 해당 글을 확인한다.
5. 글 상세 페이지에서 반응과 댓글을 남긴다.
6. 특정 문장을 하이라이트로 저장한다.
7. 마이페이지에서 저장한 문장을 다시 확인한다.
8. 글을 수정하고 검색 결과를 확인한다.
9. 권한이 없는 사용자의 수정 요청이 거부되는지 확인한다.

실행 가능한 테스트 환경이 없는 경우 테스트 인프라를 마련하고, 실행할 수 없는 테스트는 이유를 명확하게 기록한다.

## 12. 코드 품질 및 개발 규칙

- TypeScript의 타입을 적절히 정의하고 불필요한 `any`를 피한다.
- 공통 UI를 재사용 가능한 컴포넌트로 구현한다.
- 데이터베이스 접근 로직과 UI 로직을 분리한다.
- 서버 컴포넌트와 클라이언트 컴포넌트의 책임을 구분한다.
- 서버 전용 코드가 클라이언트 번들에 포함되지 않도록 한다.
- 모든 비동기 작업에서 로딩 및 오류 처리를 수행한다.
- 입력값 검증을 클라이언트와 서버 모두에서 수행한다.
- 실제 데이터의 상태와 UI 상태가 일치하도록 한다.
- 사용하지 않는 라이브러리와 불필요한 의존성을 추가하지 않는다.
- 기존 코드의 스타일과 네이밍 규칙을 따른다.
- `.env.example`에는 변수명과 예시만 작성하고 실제 비밀 값을 넣지 않는다.
- 실행 명령, 데이터베이스 설정, 초기 관리자 생성 방법을 README에 기록한다.

## 13. MVP 우선순위

개발 시간과 복잡도를 고려해 다음 우선순위를 적용한다.

### P0: 반드시 완성

- 홈 및 글 목록
- 글 상세 페이지
- Word 및 Markdown 파일 업로드
- 게시글 저장, 조회, 수정, 삭제
- 제목, 작성자, 태그 검색
- 이모지 반응
- 댓글 및 소감
- 문장 하이라이트 저장 및 복원
- 마이페이지
- 사용자 식별 및 권한 검증
- 기본적인 반응형 UI

### P1: 핵심 이후 구현

- 관리자 사용자 관리
- 알림
- 인기 글 정렬 고도화
- 신고 및 콘텐츠 관리
- 추가 검색 필터
- 사용자 프로필 설정

- 대댓글
- 고급 추천 시스템
- 이메일 및 푸시 알림
- 글쓰기 에디터 내장
- 통계 및 개인화 기능

P0가 실제로 작동하기 전에 P1이나 P2의 기능을 우선 개발하지 않는다.

## 15. 지금부터 수행할 작업

이제 실제 개발을 시작한다.

**첫 번째 작업**

현재 저장소를 분석하고 다음 사항을 간결하게 보고한다.

1. 현재 프로젝트 상태
2. 기존 기술 스택과 구조
3. 발견한 문제 및 제약
4. 개발할 기능과 우선순위
5. 권장 아키텍처와 주요 설계 결정
6. 실행할 작업 순서

**두 번째 작업**

분석이 끝나면 계획만 제시하고 기다리지 말고, 기존 프로젝트에 맞게 필요한 파일을 생성하거나 수정하면서 Phase 0과 Phase 1을 진행한다.

**세 번째 작업**

UI가 준비되면 데이터베이스와 인증을 연동하고 P0 기능을 순서대로 완성한다. 각 기능의 구현 후에는 테스트와 실제 동작을 검증한다.

**네 번째 작업**

완료한 기능, 실행한 테스트, 테스트 결과, 실행 방법, 남은 작업을 문서화한다.

### 에이전트의 최종 보고 형식

개발을 마치거나 작업을 중단해야 하는 시점에는 다음 형식으로 보고한다.

1. **구현 완료:** 실제로 동작하는 기능
2. **변경 파일:** 주요 생성 및 수정 파일과 역할
3. **실행 방법:** 설치, 환경 설정, 실행 명령
4. **데이터베이스:** 마이그레이션 및 초기 설정 방법
5. **테스트 결과:** 실행한 명령과 실제 결과
6. **보안 및 제한 사항:** 확인한 위험과 해결되지 않은 문제
7. **미완성 작업:** 구현하지 못한 기능과 이유
8. **다음 작업:** 우선적으로 수행할 작업

코드를 작성하지 않은 기능은 완료로 표시하지 않는다. 외부 서비스 연결이나 사용자 자격 증명이 필요한 작업은 필요한 설정을 명확히 안내한다.

**최우선 목표는 완성도 높은 기획 문서가 아니라, 핵심 기능이 실제로 연결되고 실행 가능한 에세이 글쓰기 플랫폼 MVP를 만드는 것이다.**
